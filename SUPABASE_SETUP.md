# MediTrack AI Supabase Setup

## Current status

The website and Expo app now have optional Supabase clients, shared data adapters, a migration, RLS policies, and server-side notification functions. No Supabase project URL or publishable key was found in the repository. No project was linked, migration applied, function deployed, or live authentication/push delivery tested. Until client environment values are configured, both apps retain clearly labeled local demo mode.

## 1. Create and configure the project

1. Create one Supabase project for both applications. Use a development project first and fictional test users/medicines only.
2. In Authentication, enable email/password and choose whether email confirmation is required.
3. Add the website development URL and deployed website URL to the Auth redirect allowlist. For mobile, add the callback generated by `Linking.createURL('/')` after the app scheme is configured; the current scheme is `mobile`.
4. Copy the project URL and publishable key from the Supabase Connect dialog. The publishable key is public client configuration; it is protected by RLS, not treated as a secret.

Create local environment files from the examples:

```powershell
Copy-Item .env.example .env.local
Copy-Item mobile/.env.example mobile/.env.local
```

Set only these public values in the local files:

```dotenv
# root .env.local
VITE_SUPABASE_URL=
VITE_SUPABASE_PUBLISHABLE_KEY=
```

```dotenv
# mobile/.env.local
EXPO_PUBLIC_SUPABASE_URL=
EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
```

Do not put a service-role key, Expo access token, or cron secret in either file. The mobile app uses SecureStore for native Auth sessions; the website uses Supabase's browser session persistence.

## 2. Apply the database migration

From the repository root, install/use the Supabase CLI and link only after you have created the project:

```powershell
npx supabase login
npx supabase link --project-ref <your-project-ref>
npx supabase db push
```

The migration creates `profiles`, `medicines`, `dose_records`, `caregiver_access`, `device_push_tokens`, `notification_preferences`, `notification_events`, and `notification_delivery_logs`. It also adds owner/caregiver RLS, Auth profile creation, consent/acceptance RPCs, database outbox triggers, and a server-only due-dose enqueue/claim API. Review the migration in `supabase/migrations/` before applying it.

The website and mobile adapters share the existing `schedule[]` / `reminder_times[]` medicine contract; dose records are idempotent on medicine, date, and slot. The database is the source of truth only after the migration is applied and both local env files contain the same project's public settings.

## 3. Deploy server-side notification functions

Deploy the functions after `db push`:

```powershell
npx supabase functions deploy register-device
npx supabase functions deploy dispatch-notifications
npx supabase functions deploy check-notification-receipts
```

The Edge Functions use the project's server-side `SUPABASE_SERVICE_ROLE_KEY` environment only. Never copy it to website or mobile code. Set these server secrets through Supabase Function Secrets (or `supabase secrets set`):

- `NOTIFICATION_CRON_SECRET`: generate a long random value. Use the same value in Supabase Vault for scheduled HTTP calls.
- `EXPO_ACCESS_TOKEN`: optional Expo push access token if push security is enabled for your Expo project.

Do not paste secrets into source files, `.env.local`, SQL migrations, or chat. Supabase supplies its project URL and server keys to Edge Functions; verify the deployed function environment in the dashboard.

## 4. Configure Expo push credentials

Expo SDK 58's compatible package is `expo-notifications ~58.1.8`; `expo-secure-store ~58.0.2` is used for native session storage. The notification config plugin is enabled, but the project has no EAS project ID or push credentials yet.

From `mobile/`, configure an EAS project and development build:

```powershell
cd mobile
npx eas-cli@latest init
npx eas-cli@latest build:configure
npx eas-cli@latest build --profile development --platform android
```

For iOS, configure Apple push credentials and build an iOS development client. For Android, configure FCM v1 credentials in Expo. Install the resulting development build on a physical device (Expo Go does not support Android remote push). Expo project ID and credential setup are prerequisites; no values are invented in the repository.

After login, mobile requests notification permission, obtains an Expo Push Token, and calls the authenticated `register-device` function. Token refreshes are re-registered. Logout deactivates the current device token best-effort; receipt failures also deactivate invalid tokens.

## 5. Schedule notification workers

Database triggers retain welcome, medicine-change, and authorized caregiver events in `notification_events`. The dispatcher leaves an event queued when there is no linked device. Device registration wakes the queue, while scheduled invocations handle retries and due-dose reminders.

Enable Supabase `pg_cron`, `pg_net`, and Vault if they are not enabled. Store the same `NOTIFICATION_CRON_SECRET` in Vault and the Edge Function secrets. Schedule POST requests to the deployed `dispatch-notifications` endpoint every minute and `check-notification-receipts` every 15 minutes. Use the project URL shown in your own dashboard; do not copy a made-up URL. The scheduled request must send `Authorization: Bearer <vault secret>` and an empty JSON body. The functions validate this secret before processing globally; normal client calls are scoped to the caller's authenticated user.

Create the Vault entry through the Supabase Dashboard Vault UI so the secret is not embedded in source or committed SQL. Then run a schedule like this in the SQL Editor, replacing only `<project-ref>` with your own project reference:

```sql
select cron.schedule(
	'meditrack-dispatch-notifications',
	'* * * * *',
	$$
		select net.http_post(
			url := 'https://<project-ref>.supabase.co/functions/v1/dispatch-notifications',
			headers := jsonb_build_object(
				'Content-Type', 'application/json',
				'Authorization', 'Bearer ' || (
					select decrypted_secret
					from vault.decrypted_secrets
					where name = 'meditrack_notification_cron_secret'
				)
			),
			body := '{}'::jsonb
		);
	$$
);

select cron.schedule(
	'meditrack-check-push-receipts',
	'*/15 * * * *',
	$$
		select net.http_post(
			url := 'https://<project-ref>.supabase.co/functions/v1/check-notification-receipts',
			headers := jsonb_build_object(
				'Content-Type', 'application/json',
				'Authorization', 'Bearer ' || (
					select decrypted_secret
					from vault.decrypted_secrets
					where name = 'meditrack_notification_cron_secret'
				)
			),
			body := '{}'::jsonb
		);
	$$
);
```

Events have unique dedupe keys, workers claim them with `FOR UPDATE SKIP LOCKED`, and delivery logs are unique per event/device. Expo's network itself is not an exactly-once transport; failed or uncertain deliveries are tracked and retried best-effort.

## 6. Verify RLS before using real accounts

Use at least three fictional accounts: patient A, patient B, and caregiver C.

1. Register patient A on the website, complete email confirmation if enabled, and verify a row appears in `profiles`.
2. Log out and register patient B. Verify patient B cannot select, update, or delete patient A's medicines or doses through either client.
3. As patient A, create an invitation for caregiver C with view-only permission and patient consent. Log in as C and accept the invitation from the mobile Profile screen.
4. Verify C can read only A's records that RLS shares, cannot read B's records, and cannot edit A's medicines or log doses with view-only permissions.
5. Revoke A's grant and verify C immediately loses access. Repeat with explicit medicine-edit and dose-log permissions to test allowed actions.
6. Run the website and mobile app using the same two public env values, then log both into patient A's account. Add/edit a fictional medicine on the website and confirm it appears on mobile. Mark a dose on mobile and confirm the website's dose tracking and reports update.

## 7. Verify push events on a physical device

1. Register a new fictional patient on the website; a welcome event should remain queued while no device is linked.
2. Log in to mobile with the exact same account and grant notification permission. Confirm the device token is active in `device_push_tokens`, then verify the welcome event is delivered.
3. Add and edit a fictional medicine on the website and check the linked device receives a generic medication-update notification.
4. Set a fictional medicine reminder a few minutes ahead in the patient's profile timezone. Wait for the scheduled dispatcher and verify one dose reminder for that medicine/date/slot.
5. Invite and accept a fictional caregiver with patient consent. As that caregiver, update a medicine or dose within granted permissions and verify the patient is notified. Revoke consent and verify both access and caregiver notifications stop.
6. Inspect `notification_events`, `notification_delivery_logs`, and function logs for dedupe keys, tickets, retries, and invalid-token deactivation. Do not treat a successful Expo ticket as proof the OS displayed the notification.
